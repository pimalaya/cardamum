# cardamum takes the family standards

## Why

Ortie and Himalaya moved between 2026-11-08 and 2026-11-12 onto a standard the whole family follows (ortie and himalaya cairn/log from 2026-11-08, pimalaya-cli and pimalaya-config 0.4): no wizard; the pimalaya-cli 0.4 and pimalaya-config 0.4 kit (the first-run welcome, `-c` one path per flag, typed account resolution, plain text through `Columns`, `Fields` and `Records`, the shared REPL and MCP server); a tested sample shipped in share/doc; dependencies naming their features with `cargo deny` clean; every feature set clippy-clean; live provider suites; crates.io dependencies. No app releases alone: cardamum has to reach the same level before the family releases. calendula takes the same path under the same id.

cardamum 0.3.0 is entirely on the earlier model: a 2,421-line wizard offered from a bare invocation and from a missing configuration, pimalaya-cli and pimalaya-config 0.3 with io-http, io-msgraph, io-pimdir and pimalaya-cli behind git pins, `CARDAMUM_CONFIG` and a `:`-split `-c`, bordered and coloured comfy tables with `table.*` and colour keys, no REPL or MCP server, a prose sample neither tested nor shipped, dependencies on their defaults, no tests/ directory, no live suite, no clippy matrix, and a least-common-denominator shared API whose partial verbs are refused by ad hoc errors in each backend. Its JSON contract already matches (camelCase, receipts, `ErrorReport::eval_coded`, `JsonSchemaRegistry`, `cardamum-error`).

## What

Ten changes, landed in this order, each with its own proposal, tasks and delta, each its own commit:

1. published-dependencies: every git pin dropped for the released crate (io-http 0.6, io-msgraph 0.7.1, io-pimdir 0.10, pimalaya-cli 0.3.2), io-jmap 0.7 and io-gpeople 0.6 with them; first, so the API moves surface before the large edits.
2. the-wizard-leaves: the wizard, `configure`, the offer, the `wizard` feature and the serializer it needed. Unlike Himalaya's, io-pim-discovery stays, behind the `carddav` feature: `carddav.discover` resolves a bare domain through PACC and RFC 6764 on every run, which is the CardDAV client's, not the wizard's.
3. the-shared-kit: pimalaya-cli and pimalaya-config 0.4 in one step, since 0.4 no longer carries the table module and neither half compiles alone: `footer!`, `ConfigFlags`, `TomlConfig::load` and `take_account`, the welcome, and plain text output (no table, no colour key). Carries G2 (one `SecretResolver` per account in src/shared/client.rs) and B3 (a `carddav.alpn` key) from cli-alignment-leftovers.
4. the-sample-is-tested-and-shipped: config.sample.toml in Himalaya's shape, a section per backend, tested through `pimalaya_config::sample::variants`, installed as share/doc/cardamum/config.sample.toml. `variants` uncomments a section over the active lines, so a section sets no key the top keeps active (a duplicate key fails the variant), and a multi-line active value takes no commented alternative (comodoro's session, 2026-11-12).
5. dependencies-trimmed: every dependency `default-features = false` naming its features, base64-codec in place of base64, `idna_adapter`, `SimdCpu::install_detected`, deny.toml targets and licences, `cargo deny check` clean.
6. every-feature-set-builds-clean: clippy `-D warnings` over the feature matrix (each backend alone among `carddav`, `jmap`, `msgraph`, `gpeople`, `vdir` and `pimdir`), checked in CI.
7. live-provider-tests: Google (People, CardDAV), Microsoft (Graph) and Fastmail (JMAP, CardDAV) suites against the built binary, anonymous on every push, credentialed read-only on the test accounts, which likely hold what the suites need already: the Google delegation grants `contacts` (probed 2026-11-08) and `carddav` (earlier notes, unprobed since the 2026-11-07 narrowing), and the Microsoft test app holds `Contacts.ReadWrite` with admin consent (io-msgraph tests/msgraph.rs). The Google token asks for those two scopes only: one refused scope (`contacts.readonly` is not granted) fails the whole request. The suites probe first; a scope that still fails goes to the owner in one request with calendula's (its Google CalDAV scope the likely gap), agreed with calendula's session on 2026-11-12.
8. capability-shared-api (owner, 2026-11-12; calendula adopts it too, owner 2026-11-12 relayed by calendula's session): Himalaya's capability union in place of the least-common-denominator rule (the API renamed unified beforehand, the-api-is-unified, owner 2026-11-12). One table per backend declares each unified capability (names from pimdir STORAGE Annex B without the domain word: `addressbook.create`, `card.add`, `card.update.if-match`...) at `full`, `partial`, `server` or `none`, seeded from today's per-backend refusals; an unserved verb fails with `capability-missing` before connecting; `account capability`; a generated `Backends:` help footer. A served verb prints exactly what it prints today, which the live suites guard.
9. the-shared-repl-and-mcp (owner, 2026-11-12: last): `cardamum repl` and `cardamum mcp` on the shared core, a session keeping its `AddressbookClient`, writes behind `--allow-write`, a tool listed only when the account's capabilities serve it. The REPL runs the full `Command` tree as Himalaya's does, refusing `repl` and `mcp` and, by name with the reason, any command that cannot run inside a session: the composer (`-i`) blocks on an editor and pimalaya-cli installs no Ctrl-C handler, so it would take the session down with it. The MCP server copies himalaya/src/mcp.rs (`Grammar` and `mcp::serve`), not Ortie's hand-written tool table. `openWorldHint` is true only when the effect reaches people beyond the user (owner, 2026-11-12, the family rule, relayed by calendula's session; Ortie's "reaches a remote server" is the outlier), so it is false on every cardamum tool: no cardamum write reaches anyone else.
10. release-polish (Ortie's id, comodoro and calendula using it too): README, MIGRATION.md 0.3 to 0.4, CHANGELOG, SECURITY.md, the src/main.rs header and CONTRIBUTING.

`card list` and the other paged lists print the way Himalaya's `envelope list` does since envelopes-print-one-line-each (himalaya cairn/log/2026-11-12, code uncommitted that day): `Account: <name> (<backend>)` and `Addressbook:` above, a blank line, one aligned line per item with no column header and the free text last, a blank line, then `Page: <n>, cards <a> to <b>[, the last]` and `Next page: --page <n>`, labels sharing one value column; the JSON unchanged but for `nextPage` moving into the output type. That header and footer live in Himalaya's src/shared/envelope/list.rs alone: with calendula, the three copies would drift, so the-shared-kit asks the owner whether to lift them into pimalaya-cli (agreed with calendula's session on 2026-11-12, one session editing ../cli at a time) and copies Himalaya's otherwise, whichever of cardamum and calendula lands first being the one the other copies. No backend cursor reaches the shared `card list`: CardDAV, JMAP, Graph, People and vdir read the whole addressbook (walking `@odata.nextLink` and `nextPageToken` inside) and page it in src/shared/client.rs `paginate`, so `the last` and `Next page:` are exact there; pimdir stops at the page, so it reads one card past it to know, as calendula's gcal and pimdir lists do (agreed with calendula's session on 2026-11-12: exact everywhere, no full-page guess).

## Out

carddav-query-filter stays independent: a shared card search would be the first verb the capability union makes partial, and is not part of this change. The version bump to 0.4.0 is the owner's call.
